# DATABASE — PostgreSQL Model

PostgreSQL is the **system of record**. It stores every observed fact, normalized entity,
evidence item, inferred relationship, investigation, analyst, audit event, scan job,
alert, report, and the behavioral/stylometric profiles. Validated DDL lives in
[`docs/schemas/postgres_schema.sql`](docs/schemas/postgres_schema.sql).

## 1. Global conventions

- `id` — `UUID` PK, generated by the app (so ingestion is idempotent and sync-ready).
- Every intelligence artifact table has `source_id FK → sources.id`, `first_seen`,
  `last_seen`, `created_at`, `updated_at`.
- `metadata JSONB NOT NULL DEFAULT '{}'` for flexible artifact fields.
- `normalized_key TEXT NOT NULL` on identity tables — the canonical dedup key,
  unique per table (`UNIQUE (source_id, normalized_key)` for provenance-scoped dedup,
  plus a global unique index to prevent cross-source duplicates).
- Text uses `TEXT`; emails `CITEXT` (extension).
- Uses Postgres `citext` and `pgcrypto` (`gen_random_uuid` as fallback for app-generated ids).
- Every mutation that matters writes to `audit_events` (see §12).
- No hard deletes for intelligence data: use `status`/`deleted_at` soft-delete.

| name | TEXT UNIQUE | e.g. `synthetic-marketplace-a` |

**Rule:** every observation, entity, and evidence row traces back to a `source` whose
`access_method` must be `synthetic\|authorized\|public`. The application refuses to ingest
from sources marked otherwise at the connector boundary.

## 13. Indexing & integrity strategy

- Unique dedup indexes on every `normalized_key` within identity tables.
- Composite indexes for the hot queries: `(normalized_key)`; `actors(status)`;
  `observations(occurred_at)`; `relationships(status, confidence)`; `timeline_events(actor_id, occurred_at)`.
- `UNIQUE (source_id, kind, subject_id, occurred_at)` on observations (idempotency).
- FK cascade discipline: intelligence tables use `ON DELETE RESTRICT`; soft-delete preferred.
- Date columns: `TIMESTAMPTZ` everywhere; behavior histograms stored as arrays.

## 14. Migrations

Alembic, single-head chain. `postgres_schema.sql` is the canonical source for Phase 1;
Phase 2 will generate the initial Alembic revision from it and keep the DDL file in sync
via a drift-check test.

## 15. Relationship to Neo4j

Postgres owns **facts and review state**. Neo4j materializes the correlation index
(see `GRAPH_MODEL.md`): nodes reference `{type, postgres_uuid}`; edges mirror
`relationships` with `confidence`, `evidence_ids`, `factors`, `explanation`, `status`.
The graph synchronizer keeps them reconciled; authoritative reads come from Postgres,
traversal reads come from Neo4j.
